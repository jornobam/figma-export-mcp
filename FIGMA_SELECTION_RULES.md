# Правила анализа Figma

## Нормализация дерева

Для каждого узла сохранить stable ID, type, name, parent, ordered children, page/section, visibility, absolute bounds и собранные тексты потомков. Не считать имя слоя надёжным единственным источником истины.

Текст нормализуется отдельно для поиска и отдельно для вывода:

- Unicode normalization;
- collapse whitespace;
- case folding для case-insensitive поиска;
- `ё/е` не объединять без явной fuzzy-опции;
- оригинальное значение всегда сохранять.

## Определение карточки

Совпадение часто происходит в дочернем TEXT, но экспортируется внешний frame/group. Выбор предка оценивается по совокупности:

- повторяемость размеров среди соседей;
- наличие нескольких текстовых/графических потомков;
- одинаковая глубина;
- регулярный spacing;
- тип узла;
- имя компонента/фрейма;
- отсутствие чрезмерно большого контейнера.

Возвращать объяснение и confidence. При нескольких почти равных кандидатах требовать уточнение.

## Строки и колонки

Базовый алгоритм:

1. Получить centers и bounds кандидатов.
2. Оценить median width/height.
3. Кластеризовать по Y-center для строк с tolerance, зависящим от median height и разброса.
4. Внутри строки сортировать по X, затем стабильным tie-breaker.
5. Аналогично строить колонки по X-center.
6. Отмечать overlaps, выбросы и строки неодинаковой длины.

Нельзя использовать фиксированный tolerance в пикселях для всех файлов. Он должен настраиваться и автоматически масштабироваться.

Вложенные блоки сначала анализируются внутри общего parent/section. Нельзя смешивать визуально совпавшие по Y элементы из несвязанных секций без явного global mode.

`blockIndex` — стабильный, единично индексированный номер parent/section partition в геометрическом порядке (Y, затем X, затем node ID). `dimensionsSimilarToPeers` сравнивает ширину и высоту узла с медианой видимых узлов того же partition; допустимое отклонение по умолчанию — 15% с минимальным абсолютным допуском 1 px. Для partition из одного узла результат `false`.

## «Обложка»

Слово «обложка» — пользовательское понятие, а не гарантированный тип Figma. MCP может предложить кандидатов:

- первый элемент повторяющегося блока;
- элемент с именем/текстом, совпавшим с `обложка`, `cover`, `основная информация`;
- элемент с отличающейся структурой, но сходными размерами;
- отдельный frame перед серией карточек.

Если определение не следует однозначно из запроса и структуры, вернуть вопрос с 2–3 вариантами и counts.

## Извлечение категорий

Значения вроде RAL, фасовки, аромата и типа продукта извлекаются регулярными выражениями или lookup maps, заданными plan. MCP не должен иметь встроенного списка RAL/ароматов.

При одном узле с несколькими значениями:

- сохранять все matches;
- не выбирать первое молча;
- использовать приоритет источников, если он задан;
- иначе добавлять clarification.

## Preview evidence

Для каждого выбранного элемента можно вернуть:

- node ID;
- hierarchy path;
- row/column;
- matched text/name;
- экспортируемый ancestor;
- extracted variables;
- final remote path;
- причины выбора.

Большой manifest должен быть пагинирован. Агенту возвращается сводка плюс representative samples и anomalies.

## Защита от изменений файла

Snapshot связан с Figma version. Перед началом export job проверить актуальную версию. Если файл изменился после preview, остановить выполнение и потребовать пересоздать план, если только пользователь заранее не подтвердил экспорт зафиксированной исторической версии и API её поддерживает.
