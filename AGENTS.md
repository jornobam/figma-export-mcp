# Инструкции автономному разработчику

## Цель

Разработай полностью работающий универсальный MCP-сервер для массового экспорта графических узлов из Figma и доставки результата в один аккаунт Яндекс Диска. Это не прототип и не набор заглушек: итог должен устанавливаться и работать на Linux, macOS и Windows.

## До начала реализации

1. Полностью прочитай `TASK.md` и все документы, перечисленные в `README.md`.
2. Проверь актуальную официальную документацию MCP SDK, Figma REST API и Яндекс Диск REST API.
3. Зафиксируй важные новые решения в `docs/DECISIONS.md`.
4. Не изменяй продуктовую область без явного обоснования.

## Обязательные ограничения

- Конечный продукт — MCP-сервер. Не создавай пользовательский CLI и не превращай проект в CLI-first продукт.
- Допустим технический executable/entrypoint, запускающий STDIO MCP.
- Первый релиз обязан поддерживать STDIO. Streamable HTTP проектируется как совместимый дополнительный транспорт и может быть реализован после полного STDIO MVP.
- Логика выбора узлов должна быть универсальной и декларативной. Не добавляй ветвления, завязанные на WABE, RAL или конкретные названия слоёв.
- Массовый экспорт разрешён только для подтверждённого плана с неизменившимся digest.
- Figma используется только на чтение.
- Локальные временные файлы удаляются только после удалённой проверки всех ожидаемых файлов.
- При частичной ошибке состояние сохраняется, а повторный запуск не загружает уже проверенные файлы заново.
- Секреты читаются из окружения или системного secret store. Никогда не логируй их.
- Все пути и имена должны одинаково обрабатываться на Linux, macOS и Windows.

## Технологические предпочтения

- Node.js 20+ и TypeScript в strict mode.
- Официальный MCP SDK; актуальную стабильную версию проверь перед фиксацией.
- Zod и/или JSON Schema для всех входов инструментов и export plan.
- Нативные `fetch`, `stream/promises` и кроссплатформенные API Node, если этого достаточно.
- Минимум тяжёлых зависимостей.
- Vitest или эквивалент для unit/integration tests.
- Форматирование и линтинг должны запускаться одной командой.

## Качество реализации

- Инструменты MCP должны быть крупнозернистыми, идемпотентными там, где возможно, и возвращать структурированные результаты.
- Для больших результатов используй пагинацию, локальные resource URI или компактные сводки; не возвращай всё дерево Figma в контекст модели.
- Все ошибки должны иметь стабильный код, понятное сообщение, признак повторяемости и безопасные детали.
- У каждого фонового задания должен быть `job_id`, журнал стадий и возможность продолжения.
- Не полагайся на порядок обхода JSON: порядок вычисляется явно.
- Не определяй «обложку», «строку» или бизнес-категорию без оценки уверенности и доступного объяснения.

## Проверка

Перед завершением:

1. Запусти typecheck, lint и все тесты.
2. Запусти MCP Inspector или эквивалентную проверку протокола.
3. Проведи end-to-end тест с mock-серверами Figma и Яндекс Диска.
4. Если пользователь предоставит тестовые токены, проведи отдельный opt-in live smoke test; тесты по умолчанию не должны требовать секретов.
5. Проверь установку на Linux и как минимум статическую совместимость путей/entrypoint для macOS и Windows.
6. Сопоставь результат с каждым пунктом `ACCEPTANCE_CRITERIA.md`.

## Условие завершения

Не объявляй работу законченной после создания структуры, схем или моков. Готовность означает работающий MCP, тесты, документацию установки, примеры конфигурации для Codex и подтверждённый полный сценарий от Figma URL до проверенных файлов на Яндекс Диске.
